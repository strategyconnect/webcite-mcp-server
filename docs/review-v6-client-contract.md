Run the bounded local protocol check without a backend key or paid calls:

```sh
npm run build
WEBCITE_MCP_PROFILE=full node --test test/review-client-contract.test.js
```

The test creates an in-memory hosted public MCP server, confirms the advertised tools, makes exactly five mock API calls (job, saved page, exact span, disposition, binary upload), and checks returned fields. A subsequent DEV check must verify the selected immutable representation, parser-loss status, source-span GET and disposition POST with an owned synthetic asset before claiming full coverage. Do not use production data or a paid review for this check.

Hosted protocol observation on 2026-09-30: both `https://devapi.webcite.co/mcp` and `https://api.webcite.co/mcp` returned MCP health version 1.9.12 with 29 public tools. An unauthenticated initialize returned 401. A catalog-only initialize and tools/list with a non-secret placeholder header returned 200 and advertised `review_document` and `get_document_review`; neither new v6 reviewer tool was present. The placeholder was not accepted as proof of account authorization, and no tool that calls the backend was invoked. This proves the remote MCP transport and public catalog shape, not Claude UI attachment delivery or authenticated v6 behavior. Local Google Cloud auth could not refresh noninteractively, so isolated DEV3059 was not probed in this pass.

Anthropic's [remote connector guide](https://support.claude.com/en/articles/11175166-get-started-with-custom-connectors-using-remote-mcp) says Claude connects to remote MCP from Anthropic's cloud. The public endpoint is therefore the relevant network surface. The guide does not establish that a Claude chat attachment becomes `file_base64` or that a particular custom header configuration is active in this account; both require an isolated Claude account/session test after the backend stack is staged.
